# Autonomous Software Repair: A RAG-Augmented Agent for Real-Time Vulnerability Patching in CI/CD Pipelines

## Introduction and background
Modern software development relies heavily on Continuous Integration/Continuous Deployment (CI/CD) pipelines to maintain speed and quality. However, security vulnerabilities (CVEs) remain a critical bottleneck during this process. While tools like SonarQube, DAST and SAST can identify thousands of vulnerabilities, fixing them requires manual effort, often leading to a "backlog" of unpatched security risks. 
This project introduces an "Autonomous Reliable Mechanism" using an AI agent capable of not only detecting security bugs but autonomously writing patches, generating unit tests, and verifying the fix in a sandbox environment. By combining Retrieval-Augmented Generation (RAG) with a rigorous "Test-Driven Repair" loop, the agent locates vulnerabilities, generates code patches, writes regression tests, and verifies the fix in a sandboxed Docker environment. 
The present status of the project is in the architectural design and data selection phase. The main necessity to implement this is to reduce the "Mean Time to Remediate" (MTTR) for critical vulnerabilities. This usually takes weeks and we want to reduce it to minutes. An autonomous agent can reduce this to minutes, securing systems before exploits are weaponized. By implementing this project, we expect to master Agentic Software Engineering (using LLMs to interact with compilers and test suites), Dockerized Sandboxing, and Retrieval-Augmented Generation (RAG) for large codebases. 

## Statement of the Project Problem 
The central problem in Automated Program Repair (APR) is the "Plausibility vs. Correctness" gap. Large Language Models (LLMs) often generate code that looks correct (plausible) but introduces subtle bugs or breaks existing functionality (regressions). 
Current tools like GitHub Copilot are "human-in-the-loop" assistants, not autonomous agents. They lack the ability to verify their own code. Meanwhile, the number of software vulnerabilities is surging. The reports indicate a 61% year-over-year increase in discovered vulnerabilities in 2024, with critical flaws rising by 37% (Security Today, 2025). Current "Coding Agents" (like Devin or GitHub Copilot) are good in general use cases but they lack the specific rigorous feedback loops required for security patching. A security patch must be precise, and it must close the vulnerability without altering the business logic. This project investigates if we can we build a specialized agent that uses "Test-Driven Repair" to guarantee that a generated security patch is both effective and regression-free? 

## Related Work 
SWE-bench paper established the industry standard for evaluating coding agents. It revealed that state-of-the-art models (like GPT-4) could initially solve less than 2% of real-world GitHub issues when unaided (Jimenez, 2024). Major advantage in the paper is that they created the first realistic "repository-level" benchmark, moving beyond simple function completion. A major limitation is that the paper focused on "generation" but did not explore "agentic loops" (iterative self-correction) or security-specific constraints, which this project addresses. 
CyberSecEval research from Meta benchmarked the propensity of LLMs to suggest insecure code. It highlighted that models often prioritize "helpfulness" over "security," inadvertently suggesting vulnerable patterns (Bhatt, 2024). This research Provides a clear metric for measuring "insecure code generation," which is critical for a security-focused agent. But a drawback is that It evaluates the model's output in isolation but does not test the model's ability to fix existing vulnerabilities in a live codebase. 
Xia (2023) demonstrated that a "conversational" approach i.e. when the model is fed back its own errors, this significantly improves repair rates compared to a single-shot attempt. This Proved that iterative feedback (the core of this project's methodology) is cost-effective and powerful. But the limitations were that the feedback was limited to conversational text. But, it did not integrate an autonomous test execution environment (sandbox) to verify the fixes, meaning the "fixed" code could still be broken at runtime.
